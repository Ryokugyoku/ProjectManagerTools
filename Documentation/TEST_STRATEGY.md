# 自動テスト戦略

## 1. 基本方針

検証は変更による失敗を検出できる最小範囲を選びます。ビルド成功、自動テスト、手動目視、実機確認は証明する内容が異なるため、必要な場面では分けて扱います。

自動テストを追加・更新する対象は次のとおりです。

- 新しい振る舞い
- 不具合修正の再現条件
- 計算、入力検証、データ変換、DB操作の意味が変わる変更

文書、コメント、表示文言、型だけの整理、振る舞いを変えないスタイル調整では、既存テストの変更やフルゲートを一律に要求しません。OS通知など自動化できない確認は、必要性がある場合に未確認事項として分けます。

## 2. CUIテスト

このリポジトリでのCUIテストは、GUI操作に依存せずコマンドラインから反復実行できる、利用者または呼び出し元から見た振る舞いのテストを指します。

- 配置: `tests/cui/`
- 実行: `npm run test:cui`
- 対象: `src/lib/` の重要な公開動作、入力検証、DBクエリと変換、エラー境界
- DBアクセス: Tauri SQL境界をモックし、SQL、引数、呼び出し順、返却値変換を確認する
- 新しい重要動作を追加した場合、正常系に加えて意味のある代表的な拒否条件を確認する

カバレッジは `src/lib/calendar.ts`、`src/lib/leaveApprovals.ts`、`src/lib/wbs.ts`、`src/lib/projects.ts` を対象とし、関数・分岐100%、行・文85%以上を必須にします。

## 3. CT（組み合わせテスト）

CTは、複数条件の組み合わせが結果へ影響する処理について、因子と水準を定義し、境界値を含む組み合わせで不変条件を確認するテストです。単純な分岐には通常のCUIテストを使います。

- 配置: `tests/ct/`
- 実行: `npm run test:ct`
- テストファイルに因子、水準、組み合わせ方をコメントで残す
- 全組み合わせが過大な場合はペアワイズを基本とし、安全・永続化に関わる条件は必要に応じて全組み合わせへ広げる

営業日計算の現在の因子は次のとおりです。

| 因子 | 水準 |
| --- | --- |
| 国 | 日本、米国、英国 |
| 開始日の種類 | 営業日、週末、祝日 |
| 営業日数 | 1日、5日 |

期待する不変条件は「終了日が営業日」「開始日から終了日までに数えた営業日が入力値と一致」です。

## 4. 実行コマンド

```bash
npm test
npm run test:cui
npm run test:ct
npm run test:coverage
npm run verify
```

`npm run verify` はカバレッジ付き全テスト、フロントエンドビルド、Rustテストを順番に実行する統合ゲートです。

## 5. リスク別品質ゲート

| レベル | 変更例 | 必須確認 |
| --- | --- | --- |
| Q0 | 文書、コメント、レイアウトに影響しない表示文言のみ | 差分と関連リンクの確認 |
| Q1 | 局所的なUI、スタイル、既存処理の小変更 | 変更に対応するテスト（振る舞い変更時）と `npm run build`。UIは影響する幅・状態だけ目視 |
| Q2 | 画面構造、共有状態、計算、DB操作、権限、migration | 変更に対応するテストと `npm run verify`。UIは通常幅・狭幅の関連状態を目視 |
| Q3 | 配布、OS統合、本番データ移行 | Q2 + `npm run tauri build` + 対象OS・環境で必要な手動確認 |

- 原則として該当する最小レベルを選びます。ファイル種別ではなく、失敗時の影響でレベルを上げます。
- UI変更でもレイアウトへ影響しない文言修正なら、すべての画面幅を確認する必要はありません。
- 実行できなかった必須確認は、理由と影響する範囲を報告します。

## 6. CI

Pull Requestと`main`へのpushでは、GitHub ActionsがmacOS上で`npm run verify`を実行します。Q2・Q3ではローカルとCIを別の証拠として扱います。Q0・Q1の作業で、CIと同じフルゲートを事前に重複実行することは必須としません。
