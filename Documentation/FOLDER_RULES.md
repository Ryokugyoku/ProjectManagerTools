# フォルダー配置規約

## 1. 目的

現在の構成を保ちながら、機能追加時に「どこへ置くか」を迷わないための規約です。小さなアプリに過剰な階層を持ち込まず、必要になった時点で段階的に分割します。

## 2. 現在の基準レイアウト

```text
ProjectManagerTools/
├── AGENTS.md                 AI 作業時の最短入口
├── Documentation/           継続して守る設計・運用仕様
├── public/                  加工せず配信する静的ファイル
├── script/                  開発・ビルド補助スクリプト
├── tests/
│   ├── cui/                 公開メソッド単位のコマンドライン自動テスト
│   └── ct/                  組み合わせ条件を網羅するテスト
├── src/                     React / TypeScript フロントエンド
│   ├── assets/              バンドル対象の画像など
│   ├── features/            WBS・案件・ユーザー・設定の画面単位UI
│   ├── lib/                 UI に依存しない外部接続・データ操作
│   ├── App.tsx              ナビゲーションと共有画面状態
│   ├── App.css              現在のデザイン定義
│   └── main.tsx             React の起動点
└── src-tauri/               Tauri / Rust ネイティブ層
    ├── capabilities/        Tauri 権限
    ├── icons/               アプリ配布用アイコン
    ├── migrations/          順序付き SQLite マイグレーション
    ├── src/                 Rust 起動・プラグイン構成
    └── tauri.conf.json      ウィンドウ・ビルド・バンドル設定
```

`node_modules/`、`dist/`、`src-tauri/target/`、`src-tauri/gen/` は依存物または生成物です。原則として手作業で編集せず、設計資料の配置先にも使いません。

## 3. 配置ルール

| 変更内容 | 配置先 | 境界 |
| --- | --- | --- |
| 画面構造と画面固有の状態 | `src/features/<feature-name>/` | `App.tsx` はナビゲーションと共有状態に限定する |
| 画面の見た目とレスポンシブ定義 | `src/App.css` | 現在の視覚トークンの実装上の正本 |
| DB 呼び出しとデータ変換 | `src/lib/` | React コンポーネントや DOM を参照しない |
| 画像など import する素材 | `src/assets/` | コンポーネントと一緒にバンドルする素材だけ |
| そのまま配信する素材 | `public/` | import やビルド時変換を必要としないものだけ |
| ネイティブ初期化・Rust 処理 | `src-tauri/src/` | 表示レイアウトを持ち込まない |
| DB スキーマ変更 | `src-tauri/migrations/` | 適用済みファイルを上書きせず、新しい連番を追加する |
| 権限変更 | `src-tauri/capabilities/` | 必要最小限とし、機能実装と同時に確認する |
| 継続的な規約・設計判断 | `Documentation/` | 作業ログや一時メモは置かない |
| 再利用する開発操作 | `script/` | 製品ランタイムから呼び出さない |
| 公開メソッドの自動テスト | `tests/cui/` | 実装ファイルと同じ責務名にする |
| 組み合わせテスト | `tests/ct/` | 因子・水準・期待する不変条件を明記する |
| GitHub Actions | `.github/workflows/` | `npm run verify` を正本として呼び出す |

## 4. 分割する条件

以下の条件が発生するまでは、現在の平坦な構成を維持します。

- `App.tsx` から独立した画面が2つ以上になった場合、`src/features/<feature-name>/` を作り、画面・画面固有部品・画面固有ロジックを同じ機能内へ移す。
- 1つの表示部品が2画面以上で実際に利用された場合だけ、`src/components/` への共通化を検討する。
- 複数機能で共有する純粋な型や変換が生じた場合だけ、`src/lib/` に用途が分かる名前で追加する。
- CSS が機能単位で独立して変更される規模になった場合、対象コンポーネントと同じ機能フォルダーへ分割する。
- Rust 側にネイティブ処理が増えた場合、`lib.rs` は構成ルートに保ち、責務単位のモジュールへ分ける。

行数だけを理由に分割しません。変更理由、状態の寿命、依存先が同じものは同じ場所に保ちます。

## 5. 命名

- React コンポーネント: `PascalCase.tsx`
- TypeScript の非表示モジュール: 内容を表す `camelCase.ts`
- CSS: 対応する画面またはコンポーネント名に合わせる
- Rust: `snake_case.rs`
- DB マイグレーション: `NNNN_<変更内容>.sql`（既存番号の続き）
- 文書: 意味が判別できる `UPPER_SNAKE_CASE.md`

`utils`、`helpers`、`common` のように責務が分からない入れ物は作りません。既存名称を変更するときは、import、設定、文書を同時に更新します。

## 6. 依存方向

```text
React UI → src/lib のデータ操作 → Tauri SQL Plugin → SQLite
Tauri 設定 → Rust 起動構成 → plugin / migration
```

- `src/lib/` は React の表示状態を管理しない。
- React コンポーネントに SQL を直接書かない。
- CSS や表示文言を Rust / migration に置かない。
- マイグレーションに現在の画面都合だけのロジックを埋め込まない。

## 7. 新規フォルダー判断

AI は新規フォルダーを作る前に、次を満たすか確認します。

1. 既存の配置先では責務が混ざるか。
2. 少なくとも1つの明確な所有責務を名前で説明できるか。
3. 近い将来ではなく、今回の変更で実ファイルが必要か。

満たさない場合は既存構成を使います。大規模な再編や依存方向の変更は、実装前に案と影響範囲を提示します。
