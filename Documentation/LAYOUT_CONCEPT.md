# レイアウトコンセプト仕様書

## 1. 目的

Project Manager Tools の画面を AI や開発者が拡張するとき、現在の操作感と視覚的一貫性を保つための基準です。現行の WBS ロードマップ画面を基準とし、新機能を機械的に同じ形へ複製するのではなく、ここに定める意図を引き継ぎます。

## 2. プロダクト体験

画面の中心は「選択した案件について、責任者ごとの予定と進捗を同じ時間軸で把握し、WBSを迷わず更新する」ことです。

- ローカルファーストで、静か・軽量・集中を妨げない。
- 主要操作は説明を読まずに見つけられる。
- 情報量よりも、現在の状態と次の行動の明瞭さを優先する。
- 技術的な雰囲気は補助表現に留め、利用者向け文言は自然な日本語にする。
- 新しい装飾は、情報階層または操作理解を改善する場合だけ追加する。

## 3. 現在の画面構造

```text
App shell
├── Navigation（ホーム / WBS / 案件 / ユーザー / 設定）
├── Home screen（案件・ユーザー・WBSの概要 / 要確認WBS / 作業開始ガイド）
├── WBS overview entry（全案件・案件未設定WBSの俯瞰 / 案件別ロードマップの選択 / 案件作成への導線）
├── WBS screen
│   ├── Header（ロードマップへのタスク追加 / 準備不足の案内）
│   ├── Summary and filters（期限超過・責任者未設定 / 責任者・状態・検索）
│   ├── Milestones（選択案件の節目 / 所属案件名・案件コード / 達成状態）
│   ├── Roadmap（選択案件内の案件または責任者グループ / 固定情報列 / 日付タイムライン）
│   └── Detail drawer（選択したタスクの編集 / 子タスク追加）
├── Projects screen（案件一覧 / 基本情報 / 案件メンバー）
├── Users screen（一覧 / プロフィール登録・編集）
└── Settings screen（祝日の国・地域 / 進捗通知）
```

視線の順序は「全体または案件の表示範囲を選ぶ → 現在の要対応 → 表示条件 → マイルストーンと予定 → 選択対象の詳細」です。WBSナビゲーションを押すと中間画面を表示し、全案件と案件未設定WBSを俯瞰する全体ロードマップ、または案件カードから1案件のロードマップへ進みます。案件がない場合や新しく追加する場合は、同じ画面から案件登録へ移動します。ホームは案件、ユーザー、WBSを別々の台帳にせず、「ユーザー登録 → 案件メンバー設定 → WBS計画」の順で作業を開始できる入口にします。新規タスクはプレビュー付きの「ロードマップにタスクを追加」モーダル、既存タスクの編集は右側ドロワーで行います。選択中のタスク配下へ追加する操作は「サブタスク」に統一します。案件、ユーザー情報、共通設定は独立画面に置き、WBSの時間軸を広く保ちます。案件画面では案件基本情報とメンバーの紐づけを同じ編集面で扱います。

## 4. 視覚言語

実際の色・余白・角丸の値は `src/App.css` を実装上の正本とします。変更時は、個々の値より以下の関係を守ります。

| 要素 | 基準 |
| --- | --- |
| 背景 | 黒に近いニュートラル。弱い緑の光で奥行きを出す |
| サーフェス | 背景より一段明るい半透明のワークスペース |
| 主色 | 明るい緑。追加、完了、フォーカスなど肯定的な意味に限定 |
| 文字 | 見出しは高コントラスト、説明・日時は段階的に弱くする |
| 危険色 | 削除やエラーだけに使い、常時強調しない |
| 書体 | 本文はシステム sans-serif、技術ラベル・件数・日時は monospace |
| 形状 | ワークスペースは大きな角丸、入力は中程度、完了操作は円形 |
| 動き | 状態理解を補う短い変化のみ。`prefers-reduced-motion` を尊重 |

色を追加する前に既存の意味色で表現できないか確認します。主色を広い背景へ多用せず、重要操作の識別力を維持します。

## 5. レスポンシブ方針

- Tauri の通常ウィンドウは 900 × 720、最小値は 540 × 560 を基準とする。
- Web 表示は幅 320px まで破綻させない。現在の狭幅切替は 560px を基準とする。
- WBS画面は最大 1540px とし、広い画面ではカレンダーと詳細を並べる。その他の小規模画面では不必要に本文を伸ばさない。
- 固定高で内容を切らず、文言増加、OS の文字拡大、エラー表示に応じて縦へ伸びる構造にする。
- 狭い幅では外側余白と操作余白を縮める。主要操作の順番や意味は変えない。
- 新しい複数カラムは、狭幅で自然な1列へ並び替えられる場合だけ採用する。

ブレークポイントは端末名ではなく、内容が読めなくなる幅を根拠に変更します。

## 6. コンポーネントと操作

### 主要操作

1画面につき、最も強い塗りのボタンは原則1種類です。現在は「ロードマップにタスクを追加」が該当します。保存中や実行不能時は無効化し、二重実行を避けます。

### ロードマップと詳細

タスク名を最優先し、状態・進捗・責任者を固定情報列で確認できるようにします。ロードマップは全体表示と1案件表示を持ち、全体表示では案件未設定WBSも欠落させません。時間軸は全日程とマイルストーンを含む幅を持ち、固定情報列を残したまま明示的な横スクロールと2週間単位・今日への移動操作を提供します。月区切りと現在表示中の年月を常に示し、横スクロール後も期間を見失わないようにします。マイルストーンは案件への所属を必須とし、WBS時間軸では専用行や常時表示の名称枠を設けず、該当日を縦の色付き列と小さな記号で示します。記号へカーソルを添えるかキーボードフォーカスを移すと名称と日付を表示し、クリックで編集できます。列色は暗色画面で識別しやすい低彩度の既定パレットから選び、自由入力による過度に強い色は使用しません。案件・責任者のどちらでまとめるか切り替えられ、検索と案件・責任者・状態の絞り込みはAND条件で適用します。責任者候補は、選択した案件のメンバーに限定します。タスクは同じ案件内の親タスクを持て、サブタスクの詳細に加えてタスク行の右クリックメニューからもサブタスクを追加して任意の深さにできます。右クリックと同じメニューは Shift+F10 またはコンテキストメニューキーでも開け、今日進んだ進捗の入力と作業経緯の時系列表示もここから行えます。自分自身と子孫は親候補にせず、親を削除した場合もサブタスクは削除せず最上位へ戻します。5営業日以上で登録する場合は、完了条件が明確な小さなサブタスクとして分割するよう案内します。週末・祝日は斜線、色、祝日マーカーで判別します。中央のバーは開始日の移動、左右端は営業日数の変更に使い、キーボードの左右キーでも同じ操作を提供します。サブタスクの日程変更時は、親タスクの日程をすべての直属子タスクが収まる期間へ祖先まで追従させます。タスクを選択すると右側ドロワーで編集します。

タスクは初期状態を「編集中」とし、詳細画面の「タスクの状態を確定」で計画を確定します。編集中は理由入力なしで日程を調整でき、確定後の日程変更はロードマップから行い、リスケ理由を必須として作業経緯へ残します。日次進捗は当日の増分率として入力し、営業日単位の計画累積率を下回る場合は理由を必須とします。ホームは確定済み未完了タスクの計画比遅延を要確認として表示します。

### 削除

主要導線から視覚的に一段下げます。ただし、キーボードフォーカス時やタッチ中心の環境でも操作不能にしません。取り消せない対象や影響が拡大した場合は確認または Undo を設計します。

## 7. 必須状態

データを表示する領域には、該当する次の状態を用意します。

- 初回読み込み中
- データなし
- フィルター結果なし
- 通常表示
- 保存・更新中
- エラーと再試行

状態の判別に色だけを使いません。エラーは原因の文字列だけで終わらせず、利用者が実行できる次の操作を近くに置きます。

## 8. アクセシビリティ

- 入力には表示ラベルまたはスクリーンリーダー用ラベルを関連付ける。
- アイコンや形だけのボタンには、対象と結果が分かる `aria-label` を付ける。
- キーボードで全操作に到達でき、フォーカスリングを消さない。
- 本文と背景、状態文字と背景のコントラストを保つ。
- タッチ対象を小さくする必要がある場合も、操作可能領域はおおむね 44 × 44px を確保する。
- 拡大時に横スクロールや重なりで主要操作を失わない。

## 9. AI 生成時の判断基準

UI を生成・変更する AI は、次の順で判断します。

1. 目的、主要操作、必要な状態を言語化する。
2. 現在の情報階層に追加できるか確認する。
3. 既存の色、余白、形状、状態表現を再利用する。
4. 320px 幅、Tauri 最小ウィンドウ、通常ウィンドウでの並びを確認する。
5. キーボード、フォーカス、読み上げ名、Reduced Motion を確認する。
6. 実装と本仕様の意味が変わる場合だけ、本仕様を更新する。

AI は、依頼のない全面刷新、流行を理由にした装飾追加、固定座標中心の配置、ホバーだけで利用できる操作を生成しません。新しいデザイン方向が必要な場合は、変更する原則と利用者への効果を先に示します。

## 10. 現行実装の既知の差異

現時点で、継続して許容する既知の差異はありません。新しい差異が生じた場合は、踏襲すべき規範と混同しないようここへ記録します。

## 11. 軽量な品質ゲート

トークンと実行時間を抑えるため、変更リスクに応じて確認範囲を選びます。

| レベル | 対象 | 必須確認 |
| --- | --- | --- |
| Q0 | 文言・文書のみ | 差分確認、リンクと記述の整合 |
| Q1 | 局所的な CSS / JSX / TypeScript | Q0 + 対応する自動テスト + `npm run build` + 変更箇所だけの目視確認 |
| Q2 | 画面構造、状態、DB 操作、権限、migration | Q1 + `npm run verify` + 通常幅・狭幅の関連状態確認 |
| Q3 | 配布、OS 統合、データ移行の本番判断 | Q2 + `npm run tauri build` + 対象OSでの手動確認 |

- 原則は変更箇所に対応する最小レベルを使い、下位レベルの確認を含める。
- CSS の数値調整ごとに全配布ビルドを行わない。
- 見た目の正しさはビルド成功だけで証明しない。UI変更では、通常幅と狭幅の該当状態を目視する。
- DB や migration の正しさは画面表示だけで証明しない。
- 実行できなかった確認は、未確認として完了報告に残す。

## 12. 受け入れチェック

UI変更の完了時は、該当項目だけを短く確認します。

- 主要操作が1つに見え、次に何をするか分かる。
- 読み込み、空、通常、エラー、実行中の各変更対象状態が扱われている。
- 320px、540px、900px 付近で見切れや重なりがない。
- マウス、キーボード、読み上げ名のいずれでも操作意図が分かる。
- 既存の主色、文字階層、角丸、余白の関係を壊していない。
- 実施した品質ゲートと未確認事項を報告できる。
